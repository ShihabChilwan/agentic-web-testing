# Scenario tests: measurement protocol

Written 16 Nov 2026, before the generator was tagged and before any scenario test ran against a planted bug. This file and `scoring/scenarios/score.ts` are hashed when the tag `scenarios-v1` is made; a different hash at scoring time means the rules changed after that point and must be reported as such.

## What is measured

The scenario generator (`agent scenarios`, SPEC §6.5) adds up to 40 scenario tests (ids `SC-<n>`) to an existing generated suite (ids `TC-<n>`). The question: how many planted bugs does the suite catch with the scenario tests added, compared with the suite alone, when both run in the same executions and the differential comparator checks both?

Suites: mern-ecommerce S1, S2 and S3 and the Kutt suite: the run folders the comparator measurement used. Each gets its scenarios with `agent scenarios --from <suite folder>`.

## Bug sets

- **Headline: the sealed-2 bugs** (the second sealed set, one per app). The generator was designed and built without opening them.
- **Development data: the first set of 12 bugs** (the comparator measurement's set). The five kinds of variation points were chosen after the comparator's misses on that set were known. Results on it are reported separately, labelled as development data. They are expected to look better than the headline, and they are never pooled with it.
- No bug is excluded after results are seen. A bug may be set aside only by a list that exists in the repository at the `scenarios-v1` tag.

## Freeze rule

1. The generator is tagged `scenarios-v1` when it is done. Its freeze record is `freeze/scenarios-v1.json`: the model settings, including the provider routing, with no key.
2. The measurement happens in a fresh session that never built the generator. That session may open the sealed-2 files only once the tag exists.
3. Every scenario suite in the measurement is generated by the `scenarios-v1` code. A suite generated during development counts only if no file under `src/` changed between its commit and the tag. Otherwise it is generated again.
4. Any change after sealed-2 results are seen is a new version (`scenarios-v2`, …). The `scenarios-v1` numbers stay the reported result; a later version's numbers are reported next to them, never in their place.

## Executions

- All executions run on Google Cloud Run, from images built at the `scenarios-v1` tag. An image carries one suite, so there is one image per suite, all from the same framework commit.
- Build: `npm run eval -- cloud-context --freeze scenarios-v1 --target <name> --run <suite>-scn --variants <sealed-2 list> --scripts-dir scripts-with-scenarios --record-responses --record-pages --golden-runs 4`.
- One combined run per version: TC and SC tests in the same execution. Results are split by test id prefix.
- Correct-version runs per repeat:
  - `golden`: the base of every comparison;
  - `golden-2` and `golden-3`: with `golden`, the noise runs;
  - `golden-4`: the fresh check (false alarms).

## Detection first (no model cost)

For each suite, after `eval import --freeze scenarios-v1`:

1. `agent noise --run <imported run> --execs <golden>,<golden-2>,<golden-3>`
2. `agent compare --run <imported run> --base <golden> --other <x>` for every bug version and for `golden-4`
3. `npx tsx scoring/scenarios/score.ts detect --suite <label>=runs/<imported run> …`

Definitions (code: `score.ts`, `detectBug`):

- **Failing test:** a test that failed or errored in the bug's execution and passed in all four correct-version runs.
- **Strong difference:** a difference the comparator marks `strong` in a test (comparator version as tagged). A folded `setup-changed` finding counts as a strong difference for both origins.
- **Caught by the suite:** a failing TC test, or a TC test with a strong difference. This is the baseline, measured in the same executions.
- **Caught with scenarios:** caught by the suite, or a failing SC test, or an SC test with a strong difference.
- **Added by scenarios:** caught with scenarios and not by the suite.
- **Comparator-only:** caught, with no failing test of either origin.
- **False alarms:** in the fresh check (`golden-4` against `golden`), per origin: the tests with a strong difference, and the tests that failed while passing in the other correct runs.
- **Missing data:** a version without results or without a comparison is listed and counted neither caught nor missed.

Reported per suite and in total, for the headline set and the development set separately:

- bugs;
- caught by TC tests;
- caught by the suite;
- caught by SC tests;
- caught by the SC comparator;
- caught with scenarios;
- added by scenarios;
- false alarms.

## Diagnosis on a sample (after detection)

- **Sample:** 10 caught (suite, bug) pairs of the headline set, chosen by code (`score.ts sample`, seed **20261116**, fixed now, before any result). The caught pairs are sorted by suite and bug and shuffled with the seed. The first scenario-only pair and the first comparator-only pair in that order are taken when there are any. The rest is filled in that order. With fewer than 10 caught pairs, all are analysed.
- **Runs:** one analysis per pair (1 repeat): `agent analyze --run <imported run> --exec <x> --differences <compare file> --output diagnoses.scenarios.json --cost-cap 0.75 --cost-ledger <one folder for all>`. The analyzer cost cap is **$0.75** for all ten together. Pairs not analysed when the cap stops the calls are listed as not analysed.
- **Scoring:** the rules of `scoring/differential/PROTOCOL.md`, unchanged (pre-registered 11 Nov 2026, sha256 `ea7c7179a53283782924d960d2a2aa9354f65d03dc35cf391dfeb438754fbfce`).

## Cost

- **Model cost:** scenario generation, at most $1 per suite (`--cost-cap 1`); the analyzer sample, at most $0.75 in total.
- **Detection:** executions and comparisons cost no model calls.
